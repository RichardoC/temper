# M2.3 phase 3 — s256 launch failure forensics + MPS compile-cache leak fix

Date: 2026-10-20 (UTC morning). The first s256 launch
(`bench/multipl-e/runs/20261020T083420Z-s256.jsonl` — meta line only, 0 rows,
abandoned) died silently mid-first-sample; a foreground 1-sample probe
reproduced it: **SIGKILL (exit 137), no traceback, no jetsam entry, no crash
report**. This doc is the evidence chain and the fix.

## Evidence chain (cheap-to-expensive, in order)

1. **Bisect (parent-prescribed)**: 1-sample probe at steps=128 → completes
   clean (exit 0, 137.7s wall, overnight pacing); steps=256 → `Killed: 9`
   ~70–90s in, mid-first-sample. Step-count-dependent.
2. **Kernel log**: (a) `IOGPUFamily … IOGPUCommandDescriptor::prepare …
   preparedBytes != requiredBytes` faults — present during the SUCCESSFUL
   overnight s128 run too → benign noise; (b) a CPU-wake-limit violation
   (`caught waking the CPU 45132 times over ~64s, 695 wakes/s`) — but the
   overnight s128 process ALSO violated the same limit (241 wakes/s) and was
   NOT killed, and the clean 128 probe never violated → wake enforcement
   correlated but not causal.
3. **Instrumented memory probes** (poll `torch.mps.current_allocated_memory()`
   / `driver_allocated_memory()` / ru_maxrss from a watcher thread):
   - torch-side alloc **flat at 14.8 GB** (weights + transients, recycled);
   - Python RSS **~1 GB**;
   - MPS **driver-allocated grows ~1–2 GB/step WITHIN one canvas**
     (decelerating, never plateauing): 20 GB at step 0 → 335 GB at step ~205;
   - **SIGKILL at a hard ~335 GB driver-allocation cap** — three independent
     deaths landed at 335.6 / ~335 / ~335 GB.
4. **No-hooks / no-history / no-empty_cache probe dies identically** →
   temper's instrumentation hooks, `output_history` retention (KBs/step), and
   the per-step `torch.mps.empty_cache()` are all EXONERATED. (empty_cache
   every step merely slows the growth: ~1.0 vs ~1.9 GB/step — it cannot reach
   the leak, which sits below the torch allocator.)
5. **MPSGraph compile-cache count**: `created MPSGraphExecutable` kernel-log
   events = 4881 in the ~236 s probe window ≈ **20 new graph executables per
   denoise step**.

## Root cause

The vendored Dream `_sample` loop gathers the masked rows every step
(`logits[mask_index]` → `[n_mask, V]`) and runs the whole sampling tail (fp32
cast, temperature div, top-p sort/cumsum/mask, top-k mask, softmax,
multinomial) at that shape. `n_mask` changes every step → every op recompiles
for a new shape → ~20 `MPSGraphExecutable`s per step, each pinning driver
memory for the process lifetime. The driver counter therefore grows roughly
linearly with the number of DISTINCT shapes per canvas (≈ steps):

| steps | canvas-end driver counter | outcome |
|---|---|---|
| 96 (M2.2 pilot) | ~200 GB | survived (60% of cap) |
| 128 (M2.3 cell) | ~250 GB | survived (75% of cap) |
| 256 | ~335 GB at step ~205 | **SIGKILL** |

Cross-sample survival of the overnight cells is explained by shape REUSE: the
n_mask schedule repeats across samples, so the compile cache stops growing
after the first sample. This also retroactively explains the M2.2-era
"macOS killed apps system-wide" memory incident (the process ran for hours at
60–75% of the same cap under memory pressure).

## The fix (temper/model/dream_fixed.py, wired in dream.sample)

Run the whole entropy tail at a FIXED padded shape `[B, V]` with B = canvas
length (max possible masked rows). Every op then compiles ONCE per canvas and
the driver counter plateaus. Neutrality invariants:

1. All reshaped ops are RNG-FREE and ROW-WISE → per-row values identical to
   the native gathered-rows computation by construction. The single
   RNG-consuming op (`Categorical.sample` → `torch.multinomial`) keeps its
   draws for real rows because torch.multinomial on MPS has the **row-prefix
   property** — verified on this host for V=152064 and (n,B) ∈
   {(100,384), (383,384), (50,384), (384,512)}: same generator state ⇒
   `multinomial([B,V])[:n] == multinomial([n,V])`. Dummy rows discarded.
2. The `[n]`-shaped bookkeeping uses a tie-free fixed-shape key
   (`is_mask*L − arange(L)`; `topk(key, B)` returns masked positions ascending
   = native gather order, then dummies) — one compile, no stable-sort
   reliance.
3. `[1, L]`-shaped ops (full_confidence, scatter) are already fixed; the only
   remaining variable-shaped ops are the small `topk(full_confidence, k)` /
   fancy-index ops with k = per-step transfer count — compiled once per
   DISTINCT k (~3–4 per canvas), negligible.

Accepted deviation (documented in the module): the confidence STATISTIC
(instrumentation only, never feeds sampling) sums in position order vs
gathered-row order → recorded `step_confidences` may differ at fp32-ulp level.
Tokens are unaffected. Escaped valves: `TEMPER_NATIVE_DREAM_SAMPLE=1`
restores the native path; non-entropy algs, batch>1, alg_temp-random calls
delegate to native. Override is instance-scoped (the spike's "no monkeypatch"
decision is hereby explicitly reversed FOR THE ENTROPY TAIL ONLY, per M2.3
phase-3 authorization; native code files in the HF cache are untouched).

## Impact on prior cells (validity note)

The 96/128 numbers were collected under leak-but-survive conditions (the
process ran within 60–75% of the kill cap; any memory pressure event could
have truncated those cells too). The committed records/exports/results remain
valid as records of what was generated, and the patch is PROVEN
generation-neutral at the s128 config (bit-identical spot-check above), so the
cells are comparable: same sampling semantics, different memory hygiene. All
future generation (s256 and beyond) runs the fixed path by default.
